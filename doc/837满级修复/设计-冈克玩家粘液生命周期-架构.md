## 3. 选择的层次、现有接口与替代路径裁决

### 3.1 具体施法携带关系，具体返回值建立归属

新增的玩家 AuraScript 名称拟定为 `spell_gunker_gooped_player`，仅对应正298259；召唤 SpellScript 名称拟定为 `spell_gunker_gooped_player_summon`，仅对应正298125。两个实现及关系对象均落在现有 `boss_gunker.cpp`，由现有 `AddSC_boss_gunker` 注册。

AuraScript在属于2097当前实例、owner与application target是同一Player、EFFECT_2确实REAL Apply时取得具体本Aura的关联记录。这里的player/map校验是关联域，不改变首领点名，也不凭未证规则筛选外层caster。同caster、多caster和GM验证的处理均服从core真实Aura匹配结果；不满足该玩家域的298259维持原路径，不能把它写成已修机器人298259。

Apply首先`PreventDefaultAction()`，阻止通用linked handler再造一次施法；随后建立真实298125 Spell，并在prepare前将本记录的强引用写入**该具体Spell**的`Variables`，私有键拟为`Gunker.PlayerGoop.Source`。记录同时保存该Spell已生成的cast GUID与一次执行序号。不能把私有键写到Player变量或靠玩家“当前token”传递。`Spell.h:358`公开Variables；`Common.h:150–195`的AnyData可持有同一精确类型的`std::shared_ptr`；`SpellScript::GetSpell()`可读取同一Spell。这里不需修改Spell类。

真实施法构造顺序必须等价于当前`Unit::CastSpell`包装：使用298125的实际SpellInfo、Player为施法者、FULL_MASK、originalCaster参数Empty；生成相同Unit显式目标；无castItem、无CustomSpellValues；优先从CURRENT_GENERIC_SPELL，否则CURRENT_CHANNELED_SPELL复制现有cast context；再附加私有记录并`prepare(targets, 当前AuraEffect)`。不要把外层Aura caster改作originalCaster。prepare接管SpellEvent生命周期后，不在AuraScript中delete Spell，也不在返回后留存原始Spell指针。

上述显式构造是现有公共Spell API的局部使用，不是另造prepare/cast。`CopyCastContextFrom`（`Spell.cpp:7367–7390`）只复制既有白名单键，**不复制本机制私有键**；foreign或其它triggered child不会自动继承玩家关联。私有键的类型在同一文件统一，禁止混用shared_ptr/weak_ptr类型造成AnyData读取异常。

298125 SpellScript在OnPrepare确认携带的记录、cast GUID、player、Map/instance、源linked application仍有效；在**OnEffectHit / EFFECT_0 / SPELL_EFFECT_SUMMON**处理298125的effect28，先阻止该次默认effect，再按第4节的窄分支创建。它直接接收具体`TempSummon*`返回值，登记GUID和本记录的双向确认，提供后续精确回收及死亡状态记录。建立关系本身不证明反向死亡救援的历史行为。没有token的298125完全走原默认effect，含旧机器人及foreign施法；有token但已失效的施法阻止创建，不转交给当前另一个Aura。

这使因果链成为“A自身创建S并将记录写到S；S自身HIT处理取得G具体返回值并提交到同一记录”。即使同时存在A/B的两个Spell、A内部嵌套B或旁边出现foreign Goop，也不通过候选枚举选择源。逐Aura枚举只用于**按已知记录身份验证或移除**，不用于反推某只新Goop应属于谁。

### 3.2 接线就绪与共同hook的限制

进入受管Apply前必须通过实际加载映射就绪校验：`ObjectMgr::GetSpellScriptsBounds`中298125的目标脚本只有一个、enabled=true、其scriptId对应的名称字节相同且`GetSpellScriptLoader`存在；298259同effect不存在另一绑定。ObjectMgr验证可将enabled置false，`CreateSpellOrAuraScripts`跳过disabled或Load失败对象（`ObjectMgr.cpp:5578–5654`、`ScriptMgr.cpp:1377–1420`）。不能仅Validate两个法术ID存在就认为配对绑定已加载。

新298125脚本工厂必须提供SpellScript且Load无条件成功，让未携token施法也加载同一个脚本后在hook中无操作。不得因为token缺失或target不合域在Load返回false，再误称已受管。OnPrepare在记录中确认接管入口已经到达；源Aura指针不跨调用保存在Spell里。实际绑定/二进制/Validate的证明仍属于运行验收。

当前独占effect的绑定guard是语义要求：本脚本在OnApply内部启动真实施法，不能保证与另一个同effect OnApply脚本的prevent/remove保持原默认执行顺序；SpellScript的OnEffectHit也可能先创建后被另一个handlerprevent。故迁移和运行就绪均拒绝未知附加/重复/负rank绑定，**不能声称支持任意其它同effect脚本组合**，也不删除它们来满足guard。确认这种组合确需保留时，先重新审计hook组合和执行点。

缺依赖、身份不匹配或契约漂移时，已加载的玩家handler不回退grid-first：阻止受管linked Apply/Remove，记录清晰错误，不创建未经关联的G，不随便解除本Aura的DOT/stun/no-actions。Validate已使脚本整条disabled时core仍可能走原默认链，这种运行状态必须判接线失败、不可称修复已生效；脚本层不能对“自身未加载”提供承诺。

`SpellScript::GetHitDest()`只在effect hook合法（`SpellScript.cpp:589–598`）；`GetEffectValue()`返回原Spell的damage（699–708）；`GetEffectInfo()`可读当前effect；`SpellInfo::CalcDuration`（3838–3847）读取duration并应用玩家duration mod。`Spell::ExecuteLogEffectSummonObject`是公开接口（`Spell.h:657`）。这些接口足以执行上表，不能把“接口存在”当作运行等价已经验证。

非空具体返回先执行原ExecuteLogEffectSummonObject，再进行本机制提交/失败回收，保留原wild返回后的日志位置，不因未提交省掉原本会生成的召唤结果日志。真实Spell/原Creature创建继续负责现有visual和source注册；本稿未审计所有未来visual override或第三方effect脚本组合，因此这些漂移不在等价认证内。

原数据支持同步成功路径，但本方案身份不依赖AfterApply前回调。未来delay若仍保持已审wild/effect语义，token可随真实SpellEvent存活到HIT；实际创建前重新验证源记录。原非channel/零delay仍应记录为部署契约，channel、目标或effects漂移不能直接沿用这份等价结论。

### 5.3 状态与失败顺序

本link包含“源仍活”“一次执行已reserved/started/consumed/finished”“是否terminal”及每只G状态。可展示为 `Prepared → Creating → Linked`，分出`FailedNoGoop`、`LostGoop`，最终`Closing → Closed`。创建未返回时收到remove立即terminal；不得因为AfterApply跳过而重开。REAPPLY不把Linked/LostGoop恢复成Prepared。

每次创建前验证本link和当次源application；调用召唤包装后再次验证。InitSummon、周围AI通知期间可以嵌套remove、reset、死亡或离图，所以“返回非空”不等于可提交。若源在包装内失效，记录仍被本次Spell强持有；直接处理**该具体返回对象**，只回收自己的G，绝不提交给当时存在的B。

若G在绑定前已死亡，按同一具体返回对象记录dead状态；创建循环finished后重新评估第7节普通单粘液救援，不能因JustDied早于绑定而永久漏救，也不能在循环未闭合时推断只有一只。若已出world或消失且没有精确death证据，记录LostGoop，不推断死亡。原Map的排队移除不会立即delete对象，但本设计不跨未来事件保留该返回指针，也不主动调用Map drain。

创建为空、prepare失败、AI类型/绑定不符、提交被拒绝，均记录原因；已经取得的未提交G按具体返回GUID回收，不收foreign G；不给本Aura凭空补一只、不把后来的REAPPLY当重试、不用grid-first补偿。默认失败本来也可能留下DOT/stun/no-actions，本设计保留这一失败表现并将验收判fail，不能以“静默解除整个Aura”掩盖接线错误。

终结必须先撤销创建许可和双向索引再调用RemoveAura/Despawn，保证同步OnCreatureRemove、AuraRemove和Goop死亡重入幂等。**撤销是将link标terminal，不是从尚活Spell的Variables擦掉Source键**；该键须保留到Spell销毁，防止晚到HIT被误认成未携token的foreign施法而走默认。具体G已退出GUID store时查询为空即停止，不查邻居、不重选B。已撤销token的晚到HIT只标取消；已经进入包装的晚返回只回收它自己。SpellScript的Unload负责报告未消费/失败执行并释放引用，不重试；AuraScript的Unload是终结兜底，不从析构访问已不存在的世界对象。

## 6. Aura实例、重入与refresh/replacement合同

遵从`TryRefreshStackOrCreate → _TryStackingOrRefreshingExistingAura → SetStackAmount/ChangeAmount`真实分支。判断本脚本linked effect是否实际应用，必须读取该次真实owned/application mask，不能用固定spellId代替；只有真实应用了linked bit才进入本hook。这与CanStackWith读取effect元数据的periodic许可是两套判据，不能把owned mask过滤条件移植到后者。

| 场景 | 精确关联与回收合同 |
|---|---|
| P上独立A、B顺序REAL Apply | A只持S_A的token及G_A；B只持S_B及G_B。同tick无需额外归属推断。Remove A/B各自GUID，不互查 |
| P上A→B嵌套，真实规则允许共存 | 两link和两具体Spell独立；S_A的返回值只提交A，S_B只提交B；不从玩家窗口数量选源 |
| 嵌套B实际替换A | core先REAL Remove A则token_A terminal；S_A已进入包装时的晚返回回收自己的G_A，不能交B。B从新Aura建立新link |
| 同一Aura/执行回调重入 | 同link的一次执行reservation/consumed标识防重复召唤；嵌套调用不覆盖外层变量。相同application已应用effect的重复REAL本身有core断言，不能制造这条不合法轨迹测试 |
| foreign153377在任意创建回调内出现 | 没有本Spell私有token，也不是本次SummonCreature返回值，保持foreign；不能因summoner=P、entry相同、唯一窗口而捕获 |
| REAL Remove发生在HIT之前 | 源token撤销；tokenized Spell到HIT不创建，且不能回退默认effect |
| REAL Remove发生在包装内部 | pre/post两次校验，返回后回收自己的确切G；终结可早于创建完成，不依赖AfterApply |
| PreventDefaultApply或skipAfter | 本架构主动PreventDefaultAction后AfterApply原本就不调用；完成/关闭由本hook作用域、link状态和Spell生命周期承担。受管effect不设“等待After”的开放窗口 |
| 同caster同mask普通refresh | 非multislot且匹配时原Aura/脚本/link保留；REAPPLY或CHANGE_AMOUNT\|REAPPLY不带REAL，既有GUID不清、不补召、不重设G的90s寿命 |
| refresh重入/临时摘effect | REAPPLY remove-half不是终结。owned Aura/link身份保留，不能从类型列表缺失推出消失；真实IsRemoved/remove-mode发生时才终结 |
| 同castermask不同 | core返回无法refresh并尝试新Aura，再按CanStackWith裁定替换或共存；不是原Aura原地修改mask。旧REAL Remove和新REAL Apply各自处理；新mask无linked bit不创建 |
| different caster共享slot分支 | 普通hit传Empty casterGuid；共享条件成立时可refresh另一caster原Aura，未改原caster/cast GUID；仍原link，不人为造新实例 |

| Remove后再创建同ID/同caster | 新Aura新link新执行，旧token永不复活；allocator重用地址不允许继承旧关系 |

经Hubble解释纠正后的补篇MD/JSON及独立窄审的I1依据，在相同已核源码/DB2/conf/cwd/schema及无后续覆盖变化的条件下给出以下静态裁决，纠正复审仍待裁决：

- 298259与298124均非passive、非multislot、非channel，STACK_FOR_DIFF_CASTERS=false。StackAmount=0来自AuraOptions缺记录后的constructor default0，**不是读到一条CumulativeAura=0记录**；AttributesCu完整最终值仍未dump。
- 当前静态StackAmount0使different-caster共享slot条件false；普通hit会填caster GUID。同caster同mask条件满足时refresh原Aura，即使stack cap0将增长钳到1仍会SetStackAmount/REAPPLY，不产生第二次REAL召唤。

- 当前所查group直接成员及递归祖先均为空，same-first-rank的group检查直接DEFAULT；数据库负spell_id在这里表示子group引用，不能当成负法术绑定。上述静态结果不认证历史自然双298259、298124+298259或每Aura恰好一Goop。
